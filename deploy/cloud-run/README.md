# Cloud Tasks / Cloud Run audio services (templates)

`audio-api.service.yaml`, `audio-worker.service.yaml`, and `audio-dispatch-recovery.job.yaml` are templates, not applied resources. Render placeholders before review. API and Worker reuse the Docker image; set `ARVC_SERVICE_ROLE=api` for API and `worker` for the private worker. Worker starts no polling loop and only exposes health plus the authenticated task endpoint. API must use `AUDIO_ANALYSIS_TRANSPORT=cloud_tasks`; local mode keeps its existing DB poller. The service templates retain `AUDIO_ANALYSIS_CLOUD_TASKS_ENABLED=false` until a production release is explicitly approved.

Grant `roles/run.invoker` on the worker only to the Cloud Tasks OIDC service account. API and Worker runtime identities need queue task creation permission and `roles/iam.serviceAccountUser` on the OIDC identity because both can enqueue (the Worker wakes the next job). The Cloud Tasks service agent must retain its Google-managed service-agent role. The task OIDC identity itself needs no database access. API/Worker runtime identities need only their database secret/network access and Cloud Tasks enqueue rights. Keep Cloud Run unauthenticated access disabled. The application also validates Google OIDC issuer, audience, expiry, and exact service-account email.

Configure Cloud Tasks `maxConcurrentDispatches=2` and `maxDispatchesPerSecond=2`. PostgreSQL claim remains the concurrency authority. Configure retry backoff and retention so task retries do not outlive the 15-minute DB job lease without a DB lease recovery path. The application has a transactional outbox and deterministic task names; a periodic Cloud Scheduler POST to `/internal/jobs/dispatch` with a distinct OIDC service account/audience is required to recover enqueue outages while API and Worker are at min instances 0. Worker completion also dispatches the next available queued jobs.

Deadlines must be kept aligned: Cloud Run request timeout 780s, task dispatch deadline 720s, job lease 900s, SCNet analysis timeout 600s. Configure Cloud Tasks queue dispatch limits to 2 concurrent / 2 per second and retain the 15-minute PostgreSQL lease recovery. The Scheduler template runs every two minutes and uses its own OIDC identity. No Cloud Run, Tasks, Scheduler, IAM, Secret Manager or Artifact Registry resource was created by this change.

## Release and stop/recovery

`.github/workflows/hosted-release-approved.yml` is workflow-dispatch only, requires explicit confirmation, reviewed project/migration inputs, and the protected `production` Environment, checks an immutable digest, verifies and applies an exact migration set, then deploys that digest with no traffic. Configure Environment reviewers and `ARVC_PRODUCTION_SUPABASE_PROJECT_REF`, `GCP_PROJECT_ID`, `GCP_REGION`, `GCP_WORKLOAD_IDENTITY_PROVIDER`, `GCP_RELEASE_SERVICE_ACCOUNT`, and secret `SUPABASE_MIGRATION_DSN`. The release identity needs only migration access and Cloud Run revision deployment rights; do not grant it broad project ownership. Route traffic and enable the Cloud Tasks kill switch only after a separately approved smoke-check decision.

To stop admission, set `AUDIO_ANALYSIS_ENABLED=false` and `AUDIO_ANALYSIS_JOBS_ENABLED=false` on the API and worker revisions, then pause the Scheduler job and disable Cloud Tasks dispatch. Existing queued rows remain in PostgreSQL and can be resumed after re-enabling the DB control row and service flags. Do not delete Storage objects or queue rows during rollback. To recover, restore the previous image digest, verify the database control switch is enabled only after the rollback is healthy, resume Scheduler/Tasks, and inspect queue/lease age. Database migrations are forward-only; use a corrective migration, never restore by dropping job tables.

## Hosted Supabase Free suitability

Step 7k-52 stores new queue audio in the private `arvc-audio-analysis` bucket. Existing bytea rows remain readable by the same claim path. The database records upload intents before Storage writes, binds objects to user/job UUID paths, and accounts active jobs, pending intents, and pending deletes against the 320 MiB global bound and 48 MiB per-user bound. Each audio object is at most 16 MiB. Terminal transitions enqueue idempotent deletion; pending-delete bytes stay reserved until object removal is finalized. API and Worker require the server-only `SUPABASE_AUDIO_STORAGE_KEY`; never expose it to Frontend or logs. The bucket is private: authenticated users can read only objects below their own user UUID path; uploads and deletes are server-only so clients cannot bypass admission or capacity accounting.

Step 7k-57b lowers Project Assets accounting from 840 MiB per owner to a **500 MiB project-wide reservation cap**. An advisory lock serializes new reservations; the trigger sums `project_assets.byte_size` across all owners and retains the 40-assets-per-owner cap. Pending upload, ready, and delete-pending rows count until finalization. Storage metadata is checked against reserved `byte_size` when the asset is finalized as ready. This is an app-managed reservation ledger, not a live measurement of Supabase's whole-project physical usage.

With the two application buckets limited to 500 MiB plus 320 MiB, app-managed stored bytes are bounded at 820 MiB. Supabase lists 1 GB included Storage on Free. The resulting headroom is approximately 140 MB if 1 GB is decimal (about 134 MiB); verify the platform's displayed usage because rounding, preexisting objects, and other buckets are outside the ledger. Do not add buckets or other Storage writers without subtracting their usage from that headroom. Check Supabase's Storage usage view before enabling admissions and during beta; stop Audio admission through `audio_analysis_control.enabled=false` before the measured project total approaches its Free quota. Project/Asset routes remain disabled in the API template via `PROJECTS_ENABLED=false`; the DB policies still permit owner-scoped authenticated Data API operations, so the project-wide trigger cap remains necessary. See [Free Storage and upload limits](https://supabase.com/docs/guides/storage/uploads/file-limits) and [Storage size usage](https://supabase.com/docs/guides/platform/manage-your-usage/storage-size). No Hosted connection or change was performed.

## Step 7k-55 Hosted Supabase Free compatibility

### Runtime DB / Storage credentials

Hosted runtime DB DSNs may use the IPv4 **Session Pooler** only on port 5432 with `sslmode=verify-full`. The application accepts only `arvc_audio_analysis.<expected-project-ref>` for audio quota/jobs and `arvc_ai_budget.<expected-project-ref>` for AI budget, and checks that the canonical `SUPABASE_URL` project ref matches the DSN target. Direct Hosted DB is accepted only for that same project and exact dedicated role. Local direct development keeps the unqualified role on loopback. Do not put a `postgres`/owner credential in a runtime DSN. This matches [Supabase's Session Pooler address and role format](https://supabase.com/docs/guides/database/connecting-to-postgres). With Cloud Run max two API and two Worker instances and Hosted pool size one per role/pool, estimated peak runtime sessions are at most 8 for audio roles (and 12 if the optional AI budget pool is enabled), below the Free shared pooler's documented default backend pool size of 15; measure actual peaks and connection wait before enabling other DB clients/features.

The API/Worker storage secret must declare an explicit `SUPABASE_AUDIO_STORAGE_KEY_KIND`. `secret_api_key` (`sb_secret_…`) is sent in `apikey` only, following [Supabase's new API-key guidance](https://supabase.com/docs/guides/getting-started/migrating-to-new-api-keys). `legacy_service_role_jwt` is accepted only when its JWT role claim is `service_role` and is sent in both `apikey` and Bearer headers. Never provide either credential to Frontend, Vite, a URL, or logs. Keep AI generation and the local fixture exemption disabled in Hosted (`AI_GENERATION_ENABLED=false`, `AI_FIXTURE_UNLIMITED_LOCAL=false`); startup also rejects enabling the local quota exemption under `AUTH_ENV=hosted`.

### Migration 017 / 018 and release workflow

The timestamp chain remains complete and unchanged. On a **new, empty Hosted project**, the first baseline applies all repository migrations in order, including `20261101001700` and `20261101001800`. Migration 017's local fixture RPC is retained for schema/history consistency, but Hosted application startup will not call it because the exemption is local-auth-only. Migration 018's pricing row update is safe only as part of the complete fresh-project baseline, before production usage exists; it must never be applied alone or retroactively to a nonempty project. Existing project data is not seeded from local environments. The workflow fails closed if 017/018 are pending without the entire local migration inventory, or if a full initial baseline is not separately confirmed empty by the operator.

Before dispatch, review the exact 14-digit pending migration list from the protected production environment and supply it in `expected_migrations` (`none` if empty), confirm `expected_project_ref`, and configure the protected variable `ARVC_PRODUCTION_POOLER_HOST` to the project's region pooler endpoint. For initial setup, confirm `confirm_fresh_project_empty` after a Dashboard/schema inspection. The workflow checks every SQL file against `deploy/hosted-migrations.sha256`, reads remote history using the secret `SUPABASE_MIGRATION_DSN`, compares [`supabase db push --dry-run`](https://supabase.com/docs/reference/cli/v1/supabase-db-push) against both migration history and the explicitly approved set, then applies only after the protected `production` Environment approval. The DSN uses `postgres.<project-ref>@<shared-pooler>:5432/postgres?sslmode=verify-full`; its project-ref user and exact protected pooler host are validated without printing credentials. No Supabase PAT/link operation is used. The workflow stops on any unrecognized output, mismatch, apply failure, or post-apply history mismatch. There is no retry, `migration repair`, or destructive rollback. An apply failure requires stopping admission and operator inspection of both schema and migration history before any corrective action.

This first-baseline policy depends on the external operator establishing that the new project has no application schema/data; migration history alone cannot prove that. If the project is not empty, do not dispatch the full baseline or try to repair its history. Stop and review a forward-only adoption plan.

### Free inactivity health check

`GET /internal/ops/supabase-health` is an optional, separately authenticated Cloud Run API route. It requires Google OIDC from a dedicated `arvc-db-healthcheck` service account with `run.invoker`; the handler calls only pgx pool `Ping` (a bounded read-only `SELECT 1`), returns 204 or a generic 503, and does not expose DSNs, hostnames, credentials, or DB error text. It does not dispatch outbox rows, run cleanup, or write PostgreSQL. The proposed `audio-db-healthcheck.job.yaml` runs every eight hours with no automatic retries; the existing two-minute `/internal/jobs/dispatch` Scheduler remains responsible only for outbox dispatch and Storage cleanup recovery. Keep `AUDIO_DB_HEALTHCHECK_ENABLED=false` until the dedicated identity, endpoint binding, schedule, and alert path have been separately approved and configured.

Detect non-2xx executions using Cloud Scheduler execution logs and Cloud Run request status logs. Before enabling the job, configure an alert policy for failed executions/503 responses and attach a reviewed email notification channel; test delivery without exposing response bodies or request headers. On failure, notify the operator, check Supabase project status and connection/migration state in the Dashboard, and keep job admission/Cloud Tasks disabled until read-only DB and permission smoke checks pass. Do not configure a tight retry loop. This light query may reduce inactivity risk but **does not guarantee Supabase Free will avoid automatic pausing**. Cloud Scheduler currently includes 3 jobs per billing account per month; additional billable jobs are listed at $0.10/job per 31 days, and the account's remaining free slots are unknown. Check current [Scheduler pricing](https://cloud.google.com/scheduler/pricing) and [Cloud Monitoring pricing](https://cloud.google.com/products/observability/pricing) before creating the schedule/alert. If creation would incur a new paid resource, stop and obtain explicit budget approval first. No Hosted or GCP resource was created by Step 7k-55.
